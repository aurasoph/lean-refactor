2. Yes. The predicted failure is reference-shape anchoring:

- Obtain a modest compiling rewrite.
- Invest further checks polishing it because it is now concrete and measurable.
- Postpone the harder structural idea.
- Start that idea too late to debug it.

That is exactly the wrong bias when implementation difficulty, rather than idea discovery, is the bottleneck. The revised wording tells the agent to test promising structural alternatives early enough to finish them.

3. Individually:

   **(a) Runner checkpoint — keep, silently.** It is bookkeeping after candidates have been checked: retain the highest-scoring fully surviving candidate by the official sum. It imposes no call cap, proof strategy, or stopping rule. It could not have caused v2/v3’s loss because they did not have it.

   **(b) “Do not inspect prior attempts” — keep.** This constrains the information set, not within-episode search. It is necessary for a clean zero-shot evaluation matching hidden tasks. It could explain v1’s advantage only if traces show v1 actually read prior solutions; in that case the result would be contaminated rather than evidence for a better search policy.

   **(c) Telling the agent about the checkpoint — drop.** Disclosure can change risk tolerance and encourage excessive checkpointing. There is no evidence that this behavioral intervention helps. The prompt no longer mentions runner recovery.

   **(d) Strategy menu — drop.** It changes the agent’s proposal distribution and can anchor search. It could plausibly have contributed to v3’s failure because v3 included inline strategy guidance, although the existing experiment cannot isolate that effect from the cap and tool restrictions.

4. My current prior is that a generic strategy menu is net-negative, not merely noise. Its advice may be individually reasonable, but enumerating moves privileges those moves over theorem-specific ideas the model might otherwise generate. There is no positive controlled evidence for it, while anchoring is a credible mechanism of harm.

I removed the entire menu. The remaining prompt explains the objective, available feedback loops, and validity constraints; it does not prescribe proof shapes.

5. My causal ranking is:

   1. **No stop rule:** the root intervention allowing continued search after an adequate candidate.
   2. **More edits:** the mechanism that generated more distinct candidate shapes.
   3. **`lake` available:** cheap error feedback made difficult implementations repairable without spending scorer calls.
   4. **More checks:** useful feedback, but partly a consequence of continued editing rather than an independent cause.
   5. **Longer wall time:** valuable mainly because it funded more edits and feedback; elapsed time alone produces nothing.
   6. **Luck/variance:** certainly nonzero, but less convincing as the primary explanation for the directional result.

These are correlated, so five single-seed problems cannot identify their separate effects. The separating experiment is a held-out factorial comparison of stop policy × `lake` access at fixed wall time, recording distinct candidate hashes, edits, compile attempts, and score-over-time. Randomized wall-time arms separate time from policy, and repeated seeds estimate variance. Scorer-query budgets with unrestricted `lake` help separate scoring checks from implementation attempts.

6. We cannot settle expected performance from five problems with one stochastic run per wrapper.

My preregistered prediction for the revised v4.1 is: on at least 30 held-out problems with three matched seeds per wrapper, equal 30-minute limits, identical tool access, and survival treated as the first criterion, its mean Σ will be within five points of v1’s mean, with no survival loss.

I would abandon the claim that this guidance wrapper is competitive with v1 if the paired 95% confidence interval for `mean Σ(v4.1 − v1)` lies entirely below −5 points.
